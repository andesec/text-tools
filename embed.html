Overview

Every tool page (mdv.html, jsv.html, pdf.html) can be embedded as an <iframe> in another web app and driven programmatically with a small postMessage protocol. The parent page sends content; the iframe renders it the same way it would for a user drag-and-drop or paste.

There is no SDK, no build step, and no cross-origin server hop — the protocol is plain browser messaging and works identically whether you embed the tools on the same origin, an https:// subdomain, or a file:// page during local development.

i

Same-origin convenience: because the tools expose no JS API on window, all communication is via postMessage. This is intentional — it works for cross-origin parents too, as long as the iframe origin is on your allowlist via the message event.origin check.

Quick start

The shortest possible embedding looks like this:

HTML 
<iframe
	id="mdv"
	src="mdv.html"
	style="width:100%; height:600px; border:0;"
></iframe>

<script>
	const iframe = document.getElementById('mdv');

	// Wait for the iframe to announce itself, then send content.
	window.addEventListener('message', (e) => {
		if (e.data?.type === 'toolSelection' && e.source === iframe.contentWindow) {
			iframe.contentWindow.postMessage({
				type: 'loadContent',
				filename: 'hello.md',
				text: '# Hello from the parent!\n\nThis is **markdown**.'
			}, '*');
		}
	});
</script>

That single loadContent message is the entire surface area for sending content. Everything else — opening files, paste, drag-and-drop, save, etc. — works inside the iframe exactly as it does when the page is opened directly.

Message spec

Parent → iframe: loadContent

Field Type Required Description
type string yes Must be the literal string "loadContent".
filename string recommended Used as the document title, for the in-page tab title, and (in jsv) to auto-detect JSON vs JS mode by extension. Falls back to "Untitled.md" / "scratchpad-N.json" / "document.pdf".
text string for mdv / jsv The plain-text content to load (Markdown for mdv, JSON/JS for jsv).
bytes ArrayBuffer for pdf Raw PDF bytes. postMessage uses structured cloning so an ArrayBuffer from File.arrayBuffer() round-trips without copying or encoding.
options object no Optional settings: targetOrigin (string) — the origin for outbound iframe messages; skipAcks (boolean) — if true, skip loadContentAck; lockFilename (boolean) — if true, user cannot rename the file.

iframe → parent: loadContentAck

After a successful load, the iframe posts an acknowledgement back to event.source:

Shape
{
  type: "loadContentAck",
  filename: "hello.md",
  format: "markdown",  // or "json" | "javascript" | "pdf"
  version: 5         // monotonic counter, starts at 1 after first load
}

Use this to chain follow-up actions ("load the next file once the previous one is acknowledged") or to distinguish successful loads from silent drops. The version field lets parents track document state and discard out-of-order messages.

Loading text into mdv.html / jsv.html

Send text + filename. The tool will:

  • Replace the editor contents (re-initialises the CodeMirror editor).
  • Update the in-page title and tab title.
  • Persist the new content to localStorage so a refresh doesn't lose it.
  • Switch to view / preview mode (mdv) or rebuild the JSON tree (jsv).
  • Send back a loadContentAck.
Send Markdown to mdv.html
mdv.contentWindow.postMessage({
  type: "loadContent",
  filename: "README.md",
  text: "# Title\n\nSome *markdown* content."
}, "*");
Send JSON to jsv.html
jsv.contentWindow.postMessage({
  type: "loadContent",
  filename: "package.json",
  text: '{"name":"my-app","version":"1.0.0"}'
}, "*");

For jsv, the filename extension determines the editor mode: .json → JSON syntax highlighting & tree view, anything else → JavaScript. The tree is also rebuilt automatically for any text that starts with { or [ even without the .json extension.

Streaming

mdv.html and jsv.html also accept content incrementally, so a host can pipe an LLM response or any chunked source straight into the editor as it arrives instead of waiting to buffer the whole document before calling loadContent.

Three message types make up the protocol:

  • appendContent — append one chunk of text to the end of the document. Send as many of these as you like.
  • streamEnd — signal that the stream is finished.
  • setViewMode — explicitly switch between "code" and "render" at any time, independent of streaming.
Field Type Required Description
type string yes "appendContent", "streamEnd", or "setViewMode".
text string appendContent only The chunk to append to the end of the current document. Appended as-is — no re-parsing or re-rendering happens per chunk.
filename string no May be sent on the first appendContent (or any later one) to set/update the document name; also accepted on streamEnd.
mode string setViewMode only "code" or "render".
options object no Same as loadContent: targetOrigin, skipAcks.

A typical stream looks like this:

  1. Optionally send a loadContent with text: '' and a filename to start from a clean, named document — or just send the first appendContent directly, which initializes the editor if none exists yet.
  2. Send one appendContent per chunk as it arrives. Each chunk is inserted at the end of the document without re-rendering, re-parsing, or writing to localStorage — this keeps a long stream cheap even at high chunk rates.
  3. Send streamEnd when the source is done.

While a stream is active, mdv.html stays pinned to the code (editor) view — it does not re-run the Markdown → HTML render pipeline on every chunk. On streamEnd it switches to render view and performs one full render of the final document. jsv.html defers JSON parsing and tree-building the same way: chunks land directly in the CodeMirror buffer, and the JSON tree is (re)built once, on streamEnd.

streamEnd acknowledges with a streamEndAck message (unless options.skipAcks is set), mirroring loadContentAck:

Shape
{
  type: "streamEndAck",
  filename: "response.md",
  format: "markdown",  // or "json" | "javascript"
  version: 6,
  length: 4218       // final document length, in characters
}

appendContent chunks are not individually acknowledged — only streamEnd replies. A subsequent plain loadContent always supersedes an in-progress stream and resets streaming state, so it's safe to abandon a stream early by just calling loadContent instead of streamEnd.

Feed a chunked response into mdv.html
async function streamInto(iframe, url, filename) {
  const res = await fetch(url);
  const reader = res.body.getReader();
  const decoder = new TextDecoder();
  const send = (msg) => iframe.contentWindow.postMessage(msg, "*");

  // Start from a clean, named document (optional).
  send({ type: "loadContent", text: "", filename: filename });

  try {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      // stream:true keeps multi-byte characters intact across chunks
      send({ type: "appendContent", text: decoder.decode(value, { stream: true }) });
    }
    const tail = decoder.decode();  // flush any trailing partial character
    if (tail) send({ type: "appendContent", text: tail });
  } finally {
    // Always finalize, even if the fetch failed partway.
    send({ type: "streamEnd", filename: filename });
  }
}

If your source is Server-Sent Events rather than a plain chunked body, do not forward res.body directly — you would paste raw data: wire frames into the editor. Parse the frames first and send only the text you extract from each one:

Parsing SSE frames before appending
let buf = "";
buf += decoder.decode(value, { stream: true });

// SSE frames are separated by a blank line.
let sep;
while ((sep = buf.indexOf("\n\n")) !== -1) {
  const frame = buf.slice(0, sep);
  buf = buf.slice(sep + 2);

  for (const line of frame.split("\n")) {
    if (!line.startsWith("data:")) continue;   // skip event:/id:/retry:
    const payload = line.slice(5).trimStart();
    if (payload === "[DONE]") continue;
    const text = JSON.parse(payload).delta;  // adapt to your schema
    if (text) send({ type: "appendContent", text });
  }
}

Streaming caveats

  • Wait for the iframe to be ready. Do not post before the tool has loaded — see the ready signal. Messages sent to a not-yet-initialized iframe are lost silently.
  • Ordering is guaranteed. postMessage is ordered per sender/receiver window pair, so rapid appendContent calls always arrive in the order you sent them. You do not need sequence numbers or to await anything between chunks.
  • Chunks may split anywhere. A chunk can end mid-word, mid-Markdown-token, or mid-UTF-8 sequence. Splitting mid-token is harmless because nothing is parsed or rendered until streamEnd. Splitting mid-UTF-8 is your problem to avoid — use TextDecoder with { stream: true } as shown above, and flush it when the body ends.
  • If streamEnd never arrives (aborted fetch, host crash), the document is left un-rendered and unsaved, and no ack is sent. Send streamEnd from a finally block. To recover an already-stranded iframe, send setViewMode with "render", or loadContent to reset entirely.
  • There is no streamError message and no timeout. Stream failure is the host's to handle. The clean reset is loadContent — it replaces the document and clears streaming state.
  • appendContent only ever appends. There is no way to retract or edit a chunk you already sent. Use loadContent when you need to replace the document.
  • Streamed text is inserted verbatim in jsv.html. The Markdown code-fence stripping that loadContent applies is deferred: it runs once at streamEnd, so an LLM emitting a fenced ```json block still parses correctly.
  • Origin validation differs by tool. mdv.html enforces options.targetOrigin and replies with origin_mismatch when it does not match the sender. jsv.html currently accepts messages from any origin and uses targetOrigin only to address its outbound replies — do not rely on it as a security boundary.

Exporting a document with its assets

Send requestAssets to get the current document back together with its images. The iframe replies with assetsResult: Markdown in which every collected image has been rewritten to a relative assets/<name> path, plus the raw bytes of each file.

This is the same pipeline behind the Save → Export with Assets (.zip) menu item, except the bundle is handed to you instead of downloaded. Use it when you need to persist or re-upload a document whose images are remote URLs or inline data: URIs. Markdown only — mdv.html. 

iframe.contentWindow.postMessage({ type: "requestAssets" }, "*");

window.addEventListener("message", (e) => {
  if (e.data?.type === "assetsResult") {
    // e.data.markdown  -> rewritten source
    // e.data.assets    -> [{ name, mime, bytes: ArrayBuffer, alt, charOffset, headingPath }]
    for (const a of e.data.assets) {
      const file = new File([a.bytes], a.name, { type: a.mime });
      // ... upload `file`, then save e.data.markdown
    }
  }
  if (e.data?.type === "error" && e.data.code === "asset_export_failed") {
    // nothing was exported — see e.data.message
  }
});

Each entry in assets carries:

Field Type Description
name string Filename inside the assets/ folder, matching the path written into the returned Markdown. Unique — collisions get a -2, -3, … suffix.
mime string The response content-type for remote images, or the data URI's own media type. May be an empty string if the server sent none.
bytes ArrayBuffer The raw file. Structured-cloneable, so it survives the origin hop intact — wrap it in a Blob or File on your side.
alt string Alt text from the image's first occurrence.
charOffset number Character offset of the first occurrence in the original document (before the rewrite).
headingPath string[] The active heading stack at that offset, outermost first — e.g. ["Guide", "Setup"]. Empty if the image appears before any heading.

Things to know

  • All-or-nothing. If any remote image fails to fetch, or any data: URI is undecodable, you get error / asset_export_failed and no bundle. There are no partial results.
  • A document with no images is a success, not an error. You get a normal assetsResult with assets: [] and the markdown unchanged, so you can handle every reply the same way and keep error for real failures.
  • Duplicates are deduped. The same URL used five times yields one asset entry and five references to the same assets/ path.
  • Bytes are never a blob: URL. An object URL is scoped to the iframe's origin and would be unreadable by your page.
  • Read-only. The editor's own buffer is untouched — the rewrite exists only in the returned markdown string. Sync version is not bumped.
  • Scope. Markdown images (![alt](url)) with http(s): or base64 data: URLs. Plain hyperlinks are deliberately left alone; angle-bracket URLs, reference-style images, and relative paths are not collected.
  • Origin is validated exactly as for loadContent — a mismatched options.targetOrigin replies origin_mismatch and the bundle is not sent.

Loading a PDF into pdf.html

Send bytes (an ArrayBuffer) + filename. The tool will:

  • Wrap the bytes in a File object and feed the existing upload pipeline.
  • Render page thumbnails.
  • Expose the page-range extraction UI just like a normal drag-and-drop.
  • Send back a loadContentAck with format: "pdf".
Send a PDF file to pdf.html
fileInput.addEventListener('change', async (e) => {
  const file = e.target.files[0];
  const buf = await file.arrayBuffer();

  pdf.contentWindow.postMessage({
    type: "loadContent",
    filename: file.name,
    bytes: buf
  }, "*");
});
i

Why ArrayBuffer? It is the most efficient binary transport that postMessage supports via structured cloning — no base64 encoding overhead, no data copies. The browser passes the buffer through directly.

Listening to the iframe

The tools also post messages upward on their own. You can use them to keep a parent UI in sync without polling.

Type When it fires Payload
ready Once on iframe load, after editor is initialized. { type, format, version } — recommended as a reliable "ready" signal before sending loadContent.
toolSelection Once on iframe load. { type, url } — the page's own URL, useful for a host app that picks the right tool. For new integrations, prefer ready instead.
contentChange On every document change (debounced 300ms). { type, text, filename, format, version, selection } — selection is { from, to }. Parents should discard version <= lastSeenVersion.
formatChange When the document format changes (e.g. JSON↔JS toggle in jsv). { type, format, previousFormat }
titleChange Whenever the document title changes (mdv picks it up from the first # heading; jsv picks it up from a title / heading / main field in the JSON). { type, title, version }
loadContentAck After a successful loadContent round-trip. { type, filename, format, version }
streamEndAck After a streamEnd round-trip. { type, filename, format, version, length }
error When an operation fails (invalid payload, parse error, etc.). { type, code, message } — codes: load_failed, validation_failed, internal_error.

Using toolSelection as a "ready" signal. A common pattern is to wait for this first outbound message before sending any loadContent, which guarantees the iframe's message listener is wired up:

Wait for iframe ready
const ready = new Promise((resolve) => {
  function onMessage(e) {
    if (e.data?.type === 'toolSelection' && e.source === iframe.contentWindow) {
      window.removeEventListener('message', onMessage);
      resolve();
    }
  }
  window.addEventListener('message', onMessage);
});

await ready;
iframe.contentWindow.postMessage({ type: 'loadContent', text: '# hi', filename: 'hi.md' }, '*');

Mismatched payloads

Each tool is opinionated about what it accepts. If you send the wrong shape, the iframe surfaces an inline toast (or, for mdv, the comments-system toast) and ignores the payload:

Sent to Wrong payload Result
mdv.html bytes only Toast: "mdv.html does not accept PDF bytes — load PDFs in pdf.html"
jsv.html bytes only Red toast: "jsv.html does not accept PDF bytes — load PDFs in pdf.html"
pdf.html text only Red toast: "pdf.html requires binary PDF bytes — use ArrayBuffer for the 'bytes' field"
!

No exceptions are thrown. The iframe silently no-ops so a single bad message in a batch never crashes the tool or your host app.

A complete, copy-pasteable host page that wires up all three tools with file pickers and a logging overlay:

Complete host page
<!doctype html>
<html>
<head>
  <meta charset="utf-8">
  <title>My App</title>
  <style>
    iframe { width: 100%; height: 400px; border: 0; display: block; }
    section { margin: 1rem 0; }
    pre { font-family: monospace; font-size: 12px; max-height: 120px; overflow: auto;
          background: #111; color: #ddd; padding: 8px; border-radius: 4px; }
  </style>
</head>
<body>

<section>
  <h2>Markdown</h2>
  <iframe id="mdv" src="mdv.html"></iframe>
</section>

<section>
  <h2>JSON</h2>
  <iframe id="jsv" src="jsv.html"></iframe>
</section>

<section>
  <h2>PDF</h2>
  <label>PDF file: <input type="file" accept="application/pdf" id="pdfFile"></label>
  <iframe id="pdf" src="pdf.html"></iframe>
</section>

<section>
  <h2>Event log</h2>
  <pre id="log"></pre>
</section>

<script>
  const log = document.getElementById('log');
  const line = (m) => log.textContent += `[${new Date().toISOString()}] ${m}\n`;

  // Capture every iframe message
  window.addEventListener('message', (e) => {
    if (e.data?.type) line(e.data.type + ' ' + JSON.stringify(e.data));
  });

  // Helper: wait for an iframe to announce itself
  function whenReady(iframe) {
    return new Promise((r) => {
      function onMsg(e) {
        if (e.data?.type === 'toolSelection' && e.source === iframe.contentWindow) {
          window.removeEventListener('message', onMsg);
          r();
        }
      }
      window.addEventListener('message', onMsg);
    });
  }

  // Send some sample content once each iframe is ready
  (async () => {
    const mdv = document.getElementById('mdv');
    const jsv = document.getElementById('jsv');
    const pdf = document.getElementById('pdf');

    await whenReady(mdv);
    mdv.contentWindow.postMessage({
      type: 'loadContent',
      filename: 'welcome.md',
      text: '# Welcome\n\nSent from the **parent** page.'
    }, '*');

    await whenReady(jsv);
    jsv.contentWindow.postMessage({
      type: 'loadContent',
      filename: 'sample.json',
      text: '{"hello":"world","items":[1,2,3]}'
    }, '*');

    await whenReady(pdf);
    document.getElementById('pdfFile').addEventListener('change', async (e) => {
      const file = e.target.files[0];
      const buf = await file.arrayBuffer();
      pdf.contentWindow.postMessage({
        type: 'loadContent',
        filename: file.name,
        bytes: buf
      }, '*');
    });
  })();
</script>
</body>
</html>

Compatibility

Feature Minimum browser Notes
Text loadContent Any modern browser Plain string — works since IE9.
Binary loadContent Chrome 43+, Firefox 20+, Safari 10.1+ Requires postMessage structured-clone support for ArrayBuffer.
PDF rendering Chrome, Firefox, Safari (latest) Uses pdf.js with a Web Worker; requires SharedArrayBuffer COOP/COEP headers only if you also use the local WASM TTS path.
file:// embedding Most browsers Works locally for development. Some browsers block postMessage across file:// origins — serve over http://localhost to be safe.

Security notes

!

Validate event.origin. The examples in this page use "*" for brevity. In a production host you should check e.origin === "https://your-iframe-origin.example.com" (or e.source === iframe.contentWindow) before trusting the message.

  • Content is sandboxed to the iframe origin. Your host page never sees the user's content unless you explicitly forward it.
  • PDFs are parsed entirely client-side in the iframe using pdf.js + pdf-lib. No bytes ever leave the browser.
  • Editor state is per-iframe in localStorage under a per-tab key, so multiple embedded instances of the same tool won't collide.
