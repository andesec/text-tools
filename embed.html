Overview

Every tool page (mdv.html, jsv.html, pdf.html) can be embedded as an <iframe> in another web app and driven programmatically with a small postMessage protocol. The parent page sends content; the iframe renders it the same way it would for a user drag-and-drop or paste.

There is no SDK, no build step, and no cross-origin server hop — the protocol is plain browser messaging and works identically whether you embed the tools on the same origin, an https:// subdomain, or a file:// page during local development.

i

Same-origin convenience: because the tools expose no JS API on window, all communication is via postMessage. This is intentional — it works for cross-origin parents too, as long as the iframe origin is on your allowlist via the message event.origin check.

Quick start

The shortest possible embedding looks like this:

HTML 
<iframe
	id="mdv"
	src="mdv.html"
	style="width:100%; height:600px; border:0;"
></iframe>

<script>
	const iframe = document.getElementById('mdv');

	// Wait for the iframe to announce itself, then send content.
	window.addEventListener('message', (e) => {
		if (e.data?.type === 'toolSelection' && e.source === iframe.contentWindow) {
			iframe.contentWindow.postMessage({
				type: 'loadContent',
				filename: 'hello.md',
				text: '# Hello from the parent!\n\nThis is **markdown**.'
			}, '*');
		}
	});
</script>

That single loadContent message is the entire surface area for sending content. Everything else — opening files, paste, drag-and-drop, save, etc. — works inside the iframe exactly as it does when the page is opened directly.

Message spec

Parent → iframe: loadContent

Field Type Required Description
type string yes Must be the literal string "loadContent".
filename string recommended Used as the document title, for the in-page tab title, and (in jsv) to auto-detect JSON vs JS mode by extension. Falls back to "Untitled.md" / "scratchpad-N.json" / "document.pdf".
text string for mdv / jsv The plain-text content to load (Markdown for mdv, JSON/JS for jsv).
bytes ArrayBuffer for pdf Raw PDF bytes. postMessage uses structured cloning so an ArrayBuffer from File.arrayBuffer() round-trips without copying or encoding.
options object no Optional settings: targetOrigin (string) — the origin for outbound iframe messages; skipAcks (boolean) — if true, skip loadContentAck; lockFilename (boolean) — if true, user cannot rename the file.

iframe → parent: loadContentAck

After a successful load, the iframe posts an acknowledgement back to event.source:

Shape
{
  type: "loadContentAck",
  filename: "hello.md",
  format: "markdown",  // or "json" | "javascript" | "pdf"
  version: 5         // monotonic counter, starts at 1 after first load
}

Use this to chain follow-up actions ("load the next file once the previous one is acknowledged") or to distinguish successful loads from silent drops. The version field lets parents track document state and discard out-of-order messages.

Loading text into mdv.html / jsv.html

Send text + filename. The tool will:

  • Replace the editor contents (re-initialises the CodeMirror editor).
  • Update the in-page title and tab title.
  • Persist the new content to localStorage so a refresh doesn't lose it.
  • Switch to view / preview mode (mdv) or rebuild the JSON tree (jsv).
  • Send back a loadContentAck.
Send Markdown to mdv.html
mdv.contentWindow.postMessage({
  type: "loadContent",
  filename: "README.md",
  text: "# Title\n\nSome *markdown* content."
}, "*");
Send JSON to jsv.html
jsv.contentWindow.postMessage({
  type: "loadContent",
  filename: "package.json",
  text: '{"name":"my-app","version":"1.0.0"}'
}, "*");

For jsv, the filename extension determines the editor mode: .json → JSON syntax highlighting & tree view, anything else → JavaScript. The tree is also rebuilt automatically for any text that starts with { or [ even without the .json extension.

Loading a PDF into pdf.html

Send bytes (an ArrayBuffer) + filename. The tool will:

  • Wrap the bytes in a File object and feed the existing upload pipeline.
  • Render page thumbnails.
  • Expose the page-range extraction UI just like a normal drag-and-drop.
  • Send back a loadContentAck with format: "pdf".
Send a PDF file to pdf.html
fileInput.addEventListener('change', async (e) => {
  const file = e.target.files[0];
  const buf = await file.arrayBuffer();

  pdf.contentWindow.postMessage({
    type: "loadContent",
    filename: file.name,
    bytes: buf
  }, "*");
});
i

Why ArrayBuffer? It is the most efficient binary transport that postMessage supports via structured cloning — no base64 encoding overhead, no data copies. The browser passes the buffer through directly.

Listening to the iframe

The tools also post messages upward on their own. You can use them to keep a parent UI in sync without polling.

Type When it fires Payload
ready Once on iframe load, after editor is initialized. { type, format, version } — recommended as a reliable "ready" signal before sending loadContent.
toolSelection Once on iframe load. { type, url } — the page's own URL, useful for a host app that picks the right tool. For new integrations, prefer ready instead.
contentChange On every document change (debounced 300ms). { type, text, filename, format, version, selection } — selection is { from, to }. Parents should discard version <= lastSeenVersion.
formatChange When the document format changes (e.g. JSON↔JS toggle in jsv). { type, format, previousFormat }
titleChange Whenever the document title changes (mdv picks it up from the first # heading; jsv picks it up from a title / heading / main field in the JSON). { type, title, version }
loadContentAck After a successful loadContent round-trip. { type, filename, format, version }
error When an operation fails (invalid payload, parse error, etc.). { type, code, message } — codes: load_failed, validation_failed, internal_error.

Using toolSelection as a "ready" signal. A common pattern is to wait for this first outbound message before sending any loadContent, which guarantees the iframe's message listener is wired up:

Wait for iframe ready
const ready = new Promise((resolve) => {
  function onMessage(e) {
    if (e.data?.type === 'toolSelection' && e.source === iframe.contentWindow) {
      window.removeEventListener('message', onMessage);
      resolve();
    }
  }
  window.addEventListener('message', onMessage);
});

await ready;
iframe.contentWindow.postMessage({ type: 'loadContent', text: '# hi', filename: 'hi.md' }, '*');

Mismatched payloads

Each tool is opinionated about what it accepts. If you send the wrong shape, the iframe surfaces an inline toast (or, for mdv, the comments-system toast) and ignores the payload:

Sent to Wrong payload Result
mdv.html bytes only Toast: "mdv.html does not accept PDF bytes — load PDFs in pdf.html"
jsv.html bytes only Red toast: "jsv.html does not accept PDF bytes — load PDFs in pdf.html"
pdf.html text only Red toast: "pdf.html requires binary PDF bytes — use ArrayBuffer for the 'bytes' field"
!

No exceptions are thrown. The iframe silently no-ops so a single bad message in a batch never crashes the tool or your host app.

Full example

A complete, copy-pasteable host page that wires up all three tools with file pickers and a logging overlay:

Complete host page
<!doctype html>
<html>
<head>
  <meta charset="utf-8">
  <title>My App</title>
  <style>
    iframe { width: 100%; height: 400px; border: 0; display: block; }
    section { margin: 1rem 0; }
    pre { font-family: monospace; font-size: 12px; max-height: 120px; overflow: auto;
          background: #111; color: #ddd; padding: 8px; border-radius: 4px; }
  </style>
</head>
<body>

<section>
  <h2>Markdown</h2>
  <iframe id="mdv" src="mdv.html"></iframe>
</section>

<section>
  <h2>JSON</h2>
  <iframe id="jsv" src="jsv.html"></iframe>
</section>

<section>
  <h2>PDF</h2>
  <label>PDF file: <input type="file" accept="application/pdf" id="pdfFile"></label>
  <iframe id="pdf" src="pdf.html"></iframe>
</section>

<section>
  <h2>Event log</h2>
  <pre id="log"></pre>
</section>

<script>
  const log = document.getElementById('log');
  const line = (m) => log.textContent += `[${new Date().toISOString()}] ${m}\n`;

  // Capture every iframe message
  window.addEventListener('message', (e) => {
    if (e.data?.type) line(e.data.type + ' ' + JSON.stringify(e.data));
  });

  // Helper: wait for an iframe to announce itself
  function whenReady(iframe) {
    return new Promise((r) => {
      function onMsg(e) {
        if (e.data?.type === 'toolSelection' && e.source === iframe.contentWindow) {
          window.removeEventListener('message', onMsg);
          r();
        }
      }
      window.addEventListener('message', onMsg);
    });
  }

  // Send some sample content once each iframe is ready
  (async () => {
    const mdv = document.getElementById('mdv');
    const jsv = document.getElementById('jsv');
    const pdf = document.getElementById('pdf');

    await whenReady(mdv);
    mdv.contentWindow.postMessage({
      type: 'loadContent',
      filename: 'welcome.md',
      text: '# Welcome\n\nSent from the **parent** page.'
    }, '*');

    await whenReady(jsv);
    jsv.contentWindow.postMessage({
      type: 'loadContent',
      filename: 'sample.json',
      text: '{"hello":"world","items":[1,2,3]}'
    }, '*');

    await whenReady(pdf);
    document.getElementById('pdfFile').addEventListener('change', async (e) => {
      const file = e.target.files[0];
      const buf = await file.arrayBuffer();
      pdf.contentWindow.postMessage({
        type: 'loadContent',
        filename: file.name,
        bytes: buf
      }, '*');
    });
  })();
</script>
</body>
</html>

Compatibility

Feature Minimum browser Notes
Text loadContent Any modern browser Plain string — works since IE9.
Binary loadContent Chrome 43+, Firefox 20+, Safari 10.1+ Requires postMessage structured-clone support for ArrayBuffer.
PDF rendering Chrome, Firefox, Safari (latest) Uses pdf.js with a Web Worker; requires SharedArrayBuffer COOP/COEP headers only if you also use the local WASM TTS path.
file:// embedding Most browsers Works locally for development. Some browsers block postMessage across file:// origins — serve over http://localhost to be safe.

Security notes

!

Validate event.origin. The examples in this page use "*" for brevity. In a production host you should check e.origin === "https://your-iframe-origin.example.com" (or e.source === iframe.contentWindow) before trusting the message.

  • Content is sandboxed to the iframe origin. Your host page never sees the user's content unless you explicitly forward it.
  • PDFs are parsed entirely client-side in the iframe using pdf.js + pdf-lib. No bytes ever leave the browser.
  • Editor state is per-iframe in localStorage under a per-tab key, so multiple embedded instances of the same tool won't collide.
